# Architectural Decisions

## 1. AI integration

The AI integration is isolated in `backend/src/modules/ai/ai.service.ts`, while `backend/src/modules/ai/ai.controller.ts` is responsible for project lookup, persistence, streaming, and summary endpoints. The current provider is Google Gemini, configured through `GEMINI_API_KEY` and instantiated with `GoogleGenerativeAI`; both chat and summary requests use the configured Gemini model. To switch providers, the main change would be replacing the SDK client and prompt/stream mapping inside `AiService`, while preserving the controller-facing methods `streamChatResponse()` and `summarizeDecisions()`. Provider failures are caught in the service and converted to `BadRequestCustomException`, and the frontend accepts only known SSE fields such as `chunk`, `text`, or `token`; there is no full schema validation or provider adapter abstraction yet, so that would be a useful future improvement for malformed responses.

## 2. Streaming

The backend exposes `GET /api/v1/projects-ai/:projectId/chat` through NestJS `@Sse()` in `backend/src/modules/ai/ai.controller.ts`. `AiService.streamChatResponse()` consumes Gemini's async stream and yields text fragments, which the controller sends as SSE events in the form `{ data: { chunk } }`, followed by `{ data: { done: true } }`. On the frontend, `frontend/src/hooks/useChatStream.ts` uses authenticated `fetch()` and `ReadableStream.getReader()` rather than `EventSource`, allowing the Bearer token to be sent in the request headers; it parses SSE frames and appends each chunk to the Zustand streaming buffer. `frontend/src/components/ChatContainer.tsx` renders that buffer immediately with a cursor indicator, then stores the accumulated assistant response when the stream completes. This keeps the implementation HTTP and reverse-proxy friendly, but it requires custom frame parsing and does not currently implement explicit abort handling or automatic retry when the connection fails.

## 3. Conversation context

For a chat request, `AiController.chatStream()` loads the project title, description, and up to the 20 oldest messages ordered by `createdAt` before calling the AI service. `AiService.buildSystemPrompt()` injects the project title and description into the instruction, and the stored history is converted to Gemini's `user` and `model` message format before the new message is appended. The assistant response is persisted as a `Message` after the stream completes, so the database remains the source of conversation history. The chat endpoint limits its prompt history to 20 messages to control token usage, while the separate summary endpoint currently loads the full project history without the same limit; a future version should apply a consistent token-based truncation or summarization policy to both paths.

## 4. State management

Conversation messages and the temporary streaming buffer live in `frontend/src/store/useChatStore.ts` because they are interactive client state that changes token by token and must update the chat UI immediately. The persistent project, message history, summary, and authentication data remain server-backed: `frontend/src/routes/projects/$projectId.tsx` loads the project with `apiRequest()`, and the backend persists messages through Prisma. `useChatStream()` uses TanStack Query's `useMutation()` only to manage the asynchronous send operation and its error state; it does not currently use a Query cache for project data. This split avoids putting a rapidly changing token buffer in a server cache, while still rehydrating the Zustand message list from the database whenever a project is opened.

## 5. What I would do differently

With two additional days, I would introduce an explicit provider interface such as `AiProvider` and add contract tests for streaming chunks, malformed provider output, rate limits, and empty responses. I would also tighten authorization in `backend/src/modules/ai/ai.controller.ts` so AI operations verify that the requested project belongs to the authenticated user, matching the ownership checks already present in `ProjectsService`. On the frontend, I would add an abort controller and a bounded retry/error classification for interrupted streams, then add an end-to-end test covering login, project navigation, seeded history, streaming, summary, and reset. These changes were deferred because the assessment slice already had the core Gemini, persistence, and progressive-rendering paths working, but they are important before treating the application as production-ready.
